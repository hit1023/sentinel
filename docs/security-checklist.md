# セキュリティ点検・防御チェックリスト

SENTINELは「ホストへの侵入」と「Webへの攻撃」の**検知**に強いが、情報漏洩の主因はそれ以外にも多い。
ここでは、日本で相次ぐ漏洩事案の傾向（取引先・委託先などの**サプライチェーン経由**の侵入、
**AIを使った自動探索**、認証情報の流出）を踏まえ、「SENTINELで見えること」と「別に点検すること」を整理する。

## 攻撃の傾向と、SENTINELの守備範囲

| 傾向 | SENTINELで見えるか | 補足 |
|---|---|---|
| 公開サービスへの自動探索（AIで高速化） | ○ `web_watch`・`auth_watch`・ATTACK MAP | 探索自体は毎日来る。重要なのは「成功したか」 |
| 認証突破（総当たり後のログイン成功） | ○ 侵入成功の相関検知（CRITICAL） | 失敗を経ない突破（漏れたパスワード・鍵）は国判定のみ |
| 侵入後の足場づくり・外部との通信 | ○ 整合性監視・プロセス/ポート・外向き通信（OUT） | `sudo`・新規ユーザー・cron追加は未対応 |
| 既知の脆弱性の悪用 | ○ 脆弱性照合（OSV.dev × CISA KEV） | OSのdpkgのみ。アプリの依存は未対応 |
| エージェントの停止・ホストの沈黙 | ○ 死活監視 | |
| **認証情報の漏洩（リポジトリ・設定への混入）** | △ 別ツール `tools/secret_scan.py` | 下記 |
| **外から見た公開面の肥大** | × 別途点検 | 下記 |
| **取引先・外部サービス・依存パッケージ経由** | × 別途点検 | 下記 |
| **AIエージェントに預けた権限の悪用**（プロンプトインジェクション） | × 別途点検 | 下記 |

## 1. 秘密情報の混入を走査する（`tools/secret_scan.py`）

外部ツールを入れずに使えるスキャナ。作業ツリーに加えて**git履歴**も見る（履歴に一度でも入った鍵は、後でファイルを消しても漏れたままのため）。
見つけた値そのものは出力しない（先頭4文字と長さのみ）。

```bash
python3 tools/secret_scan.py --root ~/docker                       # 直下の全gitリポジトリ
python3 tools/secret_scan.py --root ~/docker --visibility vis.tsv   # 公開リポジトリを強調
gh repo list <user> --limit 100 --json name,visibility -q '.[] | "\(.visibility)\t\(.name)"' > vis.tsv   # 公開/非公開の一覧
```

検出対象: AWS・GitHub・Slack・Discord・Google・Stripe・Anthropic・OpenAIのキー、秘密鍵、JWT、パスワード付きURL、
`password = "…"` 形式の代入（プレースホルダは除外）。URLスラッグなどの誤検知は、新しい形式のプレフィックスを要求して避けている。

**見つかったときの対応（優先順）**
1. **失効・再発行する**（最優先。履歴を書き換えても、すでに複製されている前提で扱う）。AWSは非アクティブ化→削除、Slack Webhookは再生成、GitHubトークンは失効。
2. 公開リポジトリなら、履歴からの除去（`git filter-repo`）と強制pushを検討する。**非破壊ではない**ので、失効の後に判断する。
3. 再発防止: 値は環境変数・`.env`（`.gitignore`）・Secret Managerに置き、GitHubの Secret Scanning と Push Protection を有効にする。

## 2. 外から見た公開面を点検する

SENTINELはホストの内側しか見ない。**インターネットから何が見えているか**は別に確認する。

- 公開IPの外部観測: `https://internetdb.shodan.io/<公開IP>`（Shodanが観測したポート・ソフトウェア・既知の脆弱性。認証不要、受動的）。
- 想定外のポートが見えたら、ルーターのポート開放とホストのファイアウォール（`ufw`）を見直す。
- SSHを公開する場合: パスワード認証OFF・rootログイン禁止・鍵のみ・fail2ban（SENTINELの相関検知と併用）。可能ならVPN（WireGuard）経由に限定する。
- 管理画面（NPM・Portainer・DNS管理・SENTINEL WebUI）は外部へ出さない。出す場合は必ず認証（NPMのAccess List、Cloudflare Access）を前段に置く。

## 3. サプライチェーン（取引先・外部サービス・依存）

- **アカウント側のログ**を定期的に見る: GitHub（Security log）、Cloudflare（Audit log）、AWS（CloudTrail）、Google（ログインアクティビティ）。不審なサインイン、トークンの新規作成、権限変更が侵入の入口になる。
- **依存パッケージ**（npm・PyPI）の脆弱性と、悪意あるパッケージの混入。`npm audit`・`pip-audit`・Dependabotを有効にする。
- **APIトークンは最小権限・期限付き**にする（フルアクセスのトークンを複数の場所に置かない）。
- 委託先・取引先に渡している権限（共有アカウント、VPN、APIキー）の棚卸し。

## 4. AIエージェントに預けた権限

AIを使った攻撃・誤操作で、いま増えている経路。ClaudeやCodex等のAIエージェントは、シェル・SSH鍵・APIトークンを使える。

- **信頼できない文章（Web・メール・ドキュメント）を読むツールと、書き込み・送信・削除ができるツールを同じエージェントに併用させない**（プロンプトインジェクション対策）。
- AIに渡す認証情報は最小権限にし、本番の管理者権限やMFA付きの鍵は渡さない。
- 外部のAIサービスへ、機密情報（顧客情報・認証情報・未公開の設計）を入力しない。入力した内容はログとして残る前提で扱う。
- MCPサーバーや拡張機能は、公開元・権限・読み書きの範囲を確認してから有効にする。承認画面でツール名と引数を読む。

## 点検の頻度の目安

| 項目 | 頻度 |
|---|---|
| 秘密情報の走査（`secret_scan.py`） | 月1回、またはリポジトリを公開する前 |
| 公開面の外部観測（InternetDB） | 月1回、ルーター・NPMの設定を変えた後 |
| アカウントの監査ログ | 週1回 |
| 依存パッケージの脆弱性 | 週1回（Dependabot等で自動化） |
| AIに渡している権限の棚卸し | 四半期 |
